# GGlearn 教材生图策略 v1 设计

## 1. 目标

GGlearn 第一版的目标不是“尽可能多出图”，而是让图片真正服务教学，同时避免输出可能误导学习者的内容。

第一版遵循以下产品原则：

- 系统自动决定一张教材图走哪条生成通道，学习者不参与技术选择。
- 判断不清楚时保守处理。
- 结果不合格时显式报错，不用静默降级掩盖失败。

## 2. 第一版范围

第一版只保留两条图通道：

- `SVG / 结构化制图`
- `图片生成`

第一版暂不纳入以下能力：

- 来源图重建
- 生图后自动叠加 SVG / HTML 标注
- 用户手动选择图通道

## 3. 两条通道的职责

### 3.1 SVG / 结构化制图

适合以下教学任务：

- 函数、坐标、几何、流程、框图
- 数学关系、算法步骤、变量对应、拓扑关系
- 需要清楚表达对象关系、步骤关系、位置对应关系的内容

### 3.2 图片生成

适合以下教学任务：

- 具象化理解
- 场景化表达
- 类比化表达
- 直觉化表达

这条通道主要用于帮助学习者建立直觉，而不是承担高精度结构表达。

## 4. 路由原则

路由不按“图长什么样”分类，而按“图在教学中承担什么任务”分类。

### 4.1 模型的职责

模型只负责做教学视觉分析，不直接决定使用 SVG 还是图片生成。

模型需要分析的问题包括：

- 这张图主要服务什么教学目标
- 它更依赖结构关系，还是更依赖具象直觉
- 是否需要丰富视觉细节才能讲明白
- 局部细节不完全精确时，是否仍不影响教学目标
- 是否适合同一小节生成两张图

### 4.2 程序的职责

程序读取模型的结构化分析结果，再做最终路由。

第一版的基本规则：

- 明显偏结构表达，走 SVG
- 明显偏直觉、类比、场景表达，走图片生成
- 判断模糊时，默认 SVG
- 一个知识点既需要严谨图，也需要直觉图时，允许同一小节生成两张图

## 5. 失败处理原则

第一版不做静默兜底。

如果图结果不合格，系统必须显式报错，并保留失败原因。

### 5.1 错误类型

至少区分三类错误：

- `路由错误`
- `生成错误`
- `系统错误`

### 5.2 诊断原则

失败不能被最终成品掩盖。

即使后续切换通道成功，也必须保留首因，例如：

- 原始选择的是哪条通道
- 为什么失败
- 是通道内失败，还是通道错配
- 是否发生了切换通道

## 6. 验收器设计

每张图必须经过两层验收：

- `规则验收`
- `教学验收`

### 6.1 规则验收

规则验收检查最低输出契约，例如：

- 输出是否合法
- 是否可读
- 是否依赖危险细节
- 是否满足该通道的基本表达要求

### 6.2 教学验收

教学验收检查：

- 这张图是否真的完成当前教学任务
- 是否比“不出图只讲文字”更有教学价值
- 是否引入新的理解歧义

### 6.3 验收结果

第一版统一使用三种结果：

- `pass`
- `fail`
- `hard_fail`

其中：

- `fail` 表示本次结果不合格，但理论上仍可重试
- `hard_fail` 表示当前通道本身不适合，不应继续在当前通道重试

## 7. SVG 通道的技术立场

第一版不建议把“模型直接手写 raw SVG”作为主方案。

更稳的做法是：

- 模型负责教学意图与图结构意图
- 成熟的结构化渲染器负责真正出图
- raw SVG 只作为最后兜底

### 7.1 选型原则

第一版不追求“一把梭覆盖全部 SVG 需求”的工具，而追求最小实用组合。

如果只选一个最接近“一个顶多个”的结构图工具，第一优先应是 `D2`。

原因：

- 它比让模型直接写 raw SVG 更稳
- 它比 Mermaid 更适合复杂结构图、关系图、教学框图
- 它更接近教材图需要的“声明式结构表达”

### 7.2 第一版最小 SVG 栈

第一版建议先收敛到以下最小组合：

- `D2`：默认结构图语言
- `Vega-Lite`：函数图、数据图、统计图
- `KaTeX`：公式渲染
- `raw SVG`：最后兜底

第一版暂不把 `Mermaid` 作为必选基础设施。

理由不是 Mermaid 无价值，而是第一版要先压低复杂度。等后续确认有大量简单流程图、时序图场景，再单独补进 Mermaid。

### 7.3 第一版 renderer 路由

第一版建议按以下方式分工：

- 默认结构图、概念关系图、模块图：`D2`
- 函数图、统计图、趋势图、数据图：`Vega-Lite`
- 复杂公式：`KaTeX`
- 极少数标准 renderer 无法覆盖的特殊图：`raw SVG`

因此第一版的 SVG 路径应当是：

`教学视觉分析 -> 选择 renderer -> 生成 renderer spec -> 编译为 SVG -> 验收`

## 8. AI 模型与接口架构

图片生成模型应独立于文本生成模型，但第一版不建议继续沿着“不断新增 xxxAiConfig”的方向扩展。

更合理的方向是：

- 统一任务接口
- 可插拔 provider adapter
- 任务到模型的路由配置

### 8.1 为什么不能只停留在 imageAiConfig

仅仅拆出 `imageAiConfig` 虽然比单一 `aiConfig` 好，但如果 GGlearn 后面要把以下任务继续拆开：

- 规划
- 讲解输出
- 图片生成
- 作答评估

那么继续新增：

- `planningAiConfig`
- `writingAiConfig`
- `imageAiConfig`
- `evaluationAiConfig`

最终会让配置和调用边界越来越乱。

### 8.2 推荐的总方向

第一版推荐的 AI 架构方向是：

- 业务层按“任务”请求能力
- AI 层按“provider endpoint”组织底层模型
- 配置层用“task routing”决定每个任务用哪个模型

也就是说，统一的是接口，不是模型。

### 8.3 第一版最小任务集合

第一版可以先按以下任务划分：

- `planning`
- `writing`
- `diagram`
- `image`
- `evaluation`

其中：

- `planning`：理解、规划、任务分解
- `writing`：正文讲解输出
- `diagram`：图意图生成、SVG spec 生成
- `image`：图片生成
- `evaluation`：验收、作答评估、质量判断

### 8.4 第一版对用户暴露的最小角色

虽然内部任务可以更细，但第一版不建议把所有任务直接暴露给用户。

第一版用户可见的模型角色只保留三类：

- `理解与规划模型`
- `讲解输出模型`
- `图片生成模型`

内部映射关系：

- `planning -> 理解与规划模型`
- `diagram -> 理解与规划模型`
- `writing -> 讲解输出模型`
- `image -> 图片生成模型`

第一版的默认策略：

- `planning` 与 `diagram` 共用一个强文本模型
- `writing` 单独暴露给用户配置，以支持成本自由
- `image` 单独暴露给用户配置
- `evaluation` 第一版可先复用 `理解与规划模型`

### 8.5 第一版最小配置骨架

第一版建议配置成两层：

- `endpoints`
- `routing`

示意结构：

```ts
type TaskType =
  | 'planning'
  | 'writing'
  | 'diagram'
  | 'image'
  | 'evaluation';

type ModelEndpoint = {
  id: string;
  label: string;
  provider: 'gemini' | 'openai' | 'openai-compatible';
  kind: 'text' | 'image' | 'multimodal';
  apiKey: string;
  baseUrl?: string;
  model: string;
};

type TaskRoutingConfig = {
  [K in TaskType]: string;
};

type AISettings = {
  endpoints: ModelEndpoint[];
  routing: TaskRoutingConfig;
};
```

### 8.6 第一版 endpoint 设计

第一版每个角色不直接绑定 provider，而是绑定到一个 `endpoint`。

也就是说：

- 用户先创建 endpoint
- 再把角色绑定到 endpoint

每个 endpoint 至少包含：

- `label`
- `provider`
- `kind`
- `apiKey`
- `model`
- `baseUrl`

其中 `label` 用于用户自定义命名，例如：

- `主力理解模型`
- `便宜讲解模型`
- `图片中转接口`

### 8.7 自定义兼容接口

第一版必须支持自定义兼容接口。

原因：

- 用户可能使用中转站
- 不同角色模型可能来自不同供应商或代理入口
- 如果只允许固定官方地址，多模型架构会在接入层被卡死

第一版 endpoint 至少支持以下 provider 类型：

- `gemini`
- `openai-compatible`

这两类 endpoint 都应允许用户填写自定义 `baseUrl`。

也就是说：

- `gemini` 不应被写死为只能走官方地址
- `openai-compatible` 当然也应允许用户自定义地址

系统可以提供默认值，但不能限制用户覆盖：

- `gemini` 默认填官方 Gemini 地址，但允许覆盖
- `openai-compatible` 默认填 OpenAI 官方地址，但允许覆盖

### 8.8 设置层的产品原则

第一版设置层应同时支持两种入口：

- `官方预设`
- `自定义接口`

但底层都统一落到同一个 endpoint 结构，不应分叉成两套不同数据模型。

这样可以兼顾：

- 普通用户：直接使用官方预设，少填字段
- 进阶用户：填写自定义 `baseUrl`、`model`、`apiKey`

### 8.9 这一架构的意义

这样设计的好处是：

- 用户可以自由接入和更换模型
- 不同任务可以在成本和效果之间做独立权衡
- 图片模型天然可以单独替换
- 后续新增规划模型、评估模型时，不需要重写业务层接口

### 8.10 第一版的明确结论

第一版应明确接受以下结论：

- 图片生成模型不应与正文模型共用同一条固定配置
- 但目标不是停在 `imageAiConfig`，而是朝 `统一任务接口 + task routing` 的结构推进
- 业务层应按任务调用 AI，而不是按 provider 直接写死逻辑
- 用户可见层只暴露三个模型角色：`理解与规划模型`、`讲解输出模型`、`图片生成模型`
- `Gemini` 与 `OpenAI-compatible` 两类 endpoint 都应允许自定义 `baseUrl`
- 设置层应支持 `官方预设 + 自定义接口` 两种入口，但底层统一为 endpoint + routing

## 9. 第一批优先试点场景

第一版最值得优先试图片生成的知识点类型：

- 机制直觉类
- 场景类比类
- 章节引导类
- 具象对象理解类

第一版不建议优先生图的类型：

- 函数、坐标、几何、流程、框图
- 依赖精确标签、数字、箭头、局部位置关系的图
- 一张图同时承担多个结构任务的内容

## 10. 第一版总策略

GGlearn 第一版的教材生图策略可以压缩成以下结论：

- 该结构化表达的，用 SVG / 结构化制图讲清楚
- 该具象化理解的，用图片生成补足
- SVG 通道要引入辅助渲染工具，不能主要依赖模型裸写 SVG
- 第一版 SVG 最小栈优先采用 `D2 + Vega-Lite + KaTeX`，raw SVG 只作兜底
- 图片生成模型必须独立于正文模型
- 整体 AI 架构应朝 `统一任务接口 + provider endpoints + task routing` 演进
- 用户可见层先暴露三个模型角色：`理解与规划模型`、`讲解输出模型`、`图片生成模型`
- 模型接入必须支持 `Gemini` 与 `OpenAI-compatible` 的自定义 `baseUrl`
- 结果不合格时显式报错，不用静默兜底掩盖真实失败
